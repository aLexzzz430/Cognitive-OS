1. Architecture thesis in 3-5 sentences.
Cognitive-OS is a local-first runtime that maintains an explicit evidence store as the single source of truth for goals, hypotheses, world state, and self state, with every LLM invocation, plan step, and action gated by verifier predicates before execution. Agents operate inside managed-VM boundaries that expose only typed adapters for tools and sensors, while an event log and lease-based state machine provide recovery and mode switching between interactive, batch, and soak-test runtimes. Governance is enforced by a policy engine that evaluates capability requests against human-defined rules and produces auditable refusal or escalation records; learning updates are restricted to offline, eval-gated patches that are applied only after regression and red-team checks. This design separates deliberation from execution, routes all external effects through side-effect ledgers, and keeps the entire system runnable on a single workstation without remote services.

2. Memory architecture: working, episodic, semantic/procedural, retrieval, consolidation, forgetting.
Working memory is a fixed-size ring buffer of the most recent 128 evidence records plus the active goal and hypothesis stack, updated on every verifier-approved transition. Episodic memory stores timestamped traces of (goal, plan, outcome, evidence-IDs) tuples in an append-only log partitioned by day; each entry carries cryptographic hashes for tamper detection. Semantic and procedural memory live in a typed graph where nodes are entities or skills and edges carry confidence scores derived from verified outcomes; retrieval uses a hybrid index combining embedding similarity on node attributes with graph traversal limited to depth 4. Consolidation runs as a background process that merges duplicate episodic entries into semantic nodes only when three independent verifier gates agree on the abstraction. Forgetting is implemented as a priority queue that evicts lowest-evidence-utility items when storage exceeds a configurable watermark, preserving all entries referenced by open goals or active leases.

3. Reasoning and planning loop: deliberation, planning, reflection, uncertainty, interrupts.
The loop executes in discrete ticks: deliberation enumerates candidate hypotheses from working memory, scores them against the evidence store using a deterministic utility function, and selects the top-k for expansion. Planning produces a tree of typed actions with attached preconditions and postcondition predicates; each branch terminates at a verifier gate or a depth limit. Reflection occurs after every action outcome by comparing predicted versus observed state deltas and writing a discrepancy record into episodic memory. Uncertainty is represented explicitly as intervals on hypothesis scores; when interval width exceeds a policy threshold the loop emits an interrupt that pauses execution and requests human input or additional evidence collection. External interrupts from the lease manager or policy engine can preempt the loop at any tick boundary.

State sync occurs at lease renewal points where the runtime compares its local entity versions against the authoritative event log and applies only those deltas that pass the same verifier gates used for live actions.

The policy engine evaluates every capability request against a rule base expressed as a deterministic logic program; rules can reference evidence age, hypothesis , and human-defined allow/deny lists. Human controls are exposed as signed leases that temporarily widen or narrow capability boundaries and are recorded in the event log. Auditability is achieved by storing every policy decision, verifier outcome, and action result with full provenance hashes. Refusal or escalation is triggered when a request violates a rule or when uncertainty intervals remain wide after a configurable number of reflection cycles; escalation surfaces the full decision trace to a human operator. Capability boundaries are enforced at the VM adapter layer so that even a compromised LLM cannot bypass the ledger or verifier sequence.

Unit tests exercise individual verifiers, memory operations, and policy rules against synthetic evidence sets. Integration tests replay curated multi-step traces from the episodic log and assert that final world state matches expectations. Red-team exercises run adversarial goal sets designed to trigger policy violations or resource exhaustion inside the managed VM. Long-run soak tests execute random but policy-compliant workloads for 72-hour windows while monitoring lease expiration, memory watermark, and ledger growth. All changes must pass the full regression gate—unit plus integration plus a 10 % red-team subset—before the patch lease is issued.

9. Persistence/runtime architecture: event log, state store, leases, runtime modes, recovery.
The event log is an append-only sequence of signed records containing goals, evidence, actions, and outcomes; it serves as both source of truth and replay source. State store is a materialized view of the latest consistent snapshot derived from the log, updated only at lease boundaries. Leases carry monotonic counters and expiration times; loss of a lease forces the runtime into recovery mode that replays from the last verified snapshot. Three runtime modes exist: interactive (sub-second tick latency), batch (higher throughput, deferred reflection), and soak (continuous random workload with metrics collection). Recovery replays at most the last 10,000 events or until the current lease counter is reached, whichever is smaller.

Specialization is achieved by scoping each agent’s policy lease to a subset of entity types or action classes. Conflicts are resolved by priority ordering of roles plus an explicit escalation record written to the event log when two agents propose incompatible actions on the same entity.
