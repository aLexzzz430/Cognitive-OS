# Architecture for AGI: COLE  
## Cognitive Orchestrated Latent Execution

COLE is an AGI architecture built on top of current LLM capabilities—not by making the LLM alone behave intelligently, but by enclosing it in a closed cognitive loop with explicit memory, planning, world modeling, tool use, safety, self-improvement, and persistence. The LLM is the interface to cognition; the architecture is the cognition.

Below is the full design across the 11 required dimensions.

---

## 1. Memory Architecture

Memory is not one store. COLE has four distinct memory systems with different formats, access patterns, and lifetimes:

### 1.1 Short-Term / Working Memory (WM)
- **Format:** A structured JSON document called the “Cognitive Blackboard.”
- **Contents:** current goal, active subgoals, belief state, recent observations, candidate plans, tool results, uncertainty flags, and the current MCTS search tree.
- **Capacity:** managed by a fixed token budget (e.g., 100K tokens for WM using the LLM context window).
- **Forgetting:** when WM exceeds budget, a `Memory Consolidation` process compresses old or redundant entries into long-term semantic memory and removes them from WM. This is not simple eviction; it is abstraction.

### 1.2 Long-Term Semantic Memory
- **Storage:** PostgreSQL with `pgvector` for embedding retrieval, plus a knowledge graph for relational facts.
- **Records:** `(subject, predicate, object, confidence, source, timestamp)`.
- **Provenance:** every fact is linked to the episode that produced it. Facts can be updated, but old versions remain in a temporal graph.
- **Retrieval:** multi-query generated by the executive: given the current WM state, an LLM generates 3–5 natural-language search queries; embeddings retrieved; results filtered by recency, relevance, and confidence; inserted into WM as “recalled knowledge.”

### 1.3 Episodic Memory
- **Format:** append-only event log stored as JSONL, each event:
  ```
  {
    id, timestamp,
    parent_id,           // causal parent event
    state_snapshot_hash,
    action,
    observation,
    reward_signal,
    alternatives_generated
  }
  ```
- **Indexing:** both by timestamp and by dense embedding of `(state + action + outcome)`.
- **Retrieval:** a query about a current situation retrieves episodes where similar situations occurred, especially those involving different outcomes. This supports counterfactual retrieval: “when did I see this state and act differently?”
- **Consolidation:** during an idle phase, an LLM-based summarizer clusters raw episodes and converts them into new semantic facts and skill statistics.

### 1.4 Procedural Memory
- **Format:** a Skill Library, not raw weights:
  ```
  skill_name, version,
  trigger_condition,     // logical predicate on WM state
  preconditions,         // required facts/resources
  program,               // code, prompt template, or LoRA adapter
  postconditions,        // expected effects
  success_rate,
  cost,
  last_used
  ```
- **Execution:** skills can be low-level tool-use scripts, high-level prompt templates, or specialized fine-tuned adapters loaded on demand.
- **Acquisition:** successful trajectories are distilled into skills by a `Skill Compiler` (an LLM + static verifier). If a plan succeeds in a simulation or real environment, the planner’s decision trace is generalized into a reusable skill with preconditions/postconditions inferred from the trace.
- **Update:** each execution updates statistics; skills with negative success rates are retracted or re-learned.

## 2. Reasoning and Planning Loop

The core loop is a Monte Carlo Tree Search (MCTS) over *latent mental states*, not raw tokens.

### 2.1 State Representation
- A state is a tuple: `(goal, belief_distribution, WM_summary, plan_queue, safety_state)`.
- The belief distribution over world states is maintained by the World Model (Section 5). The LLM is used to convert raw observations into structured belief updates.

### 2.2 MCTS over Thoughts and Actions

```
def decide(goal, belief, wm):
    root = Node(state=(goal, belief, wm))
    for _ in deliberation_budget:
        node = select(root)                 # PUCT selection
        if node is leaf:
            actions = propose_actions(node) # LLM generates K=8 actions
            for a in actions:
                predicted_state = world_model.simulate(node.state, a)
                r = reward_model(goal, predicted_state, a)
                node.add_child(a, predicted_state, r)
        backpropagate(node, r)
    return best_action(root)
```

- `propose_actions` uses the LLM with:
  - current goal
  - retrieved episodic memories from similar states
  - available skills
  - tool schemas
  - safety constraints
- Each action can be:
  - an internal thought / subgoal
  - a memory retrieval
  - a world-model query
  - a tool call
  - a request for human feedback
- `reward_model` is a learned evaluator that scores:
  - progress toward goal
  - factual consistency
  - expected success under world-model simulation
  - safety (low risk, reversible, approved)
- Selection uses PUCT with an added **novelty bonus**: actions whose predicted state is far in memory-embedding space from previously seen states are preferred when uncertainty is high.

### 2.3 Reflection and Plan Repair
When MCTS returns low value or execution fails, the system runs a **Reflection Agent**:
- Generates a post-hoc explanation: “Why did the plan fail?”
- Updates episodic memory with lesson tags.
- Modifies the plan queue, possibly rolling back to an earlier subgoal.
- If repeated failures occur, triggers skill re-learning or asks for human assistance.

## 3. Learning and Self-Improvement Mechanism

COLE self-improves through a combination of online non-parametric learning and offline parametric training.

### 3.1 Online Memory Learning
- Episodic memory is always writable.
- Skills are added and refined after every successful/failed task.
- Semantic facts are updated online.
- Online operation is the primary mode of adaptation.

### 3.2 Offline Parametric Learning
- Periodically, the system trains new LoRA adapters on trajectories stored in episodic memory.
- Training uses:
  - behavior cloning on successful trajectories
  - DPO (Direct Preference Optimization) on  chosen-vs-rejected episodes
  - next-token prediction on high-value reasoning traces
- The base LLM weights remain frozen. This avoids catastrophic forgetting and reduces alignment risk.

### 3.3 Self-Improvement Loop
1. The `Curriculum Generator` estimates current skill levels from success rate distributions.
2. It generates new tasks at the frontier (target success rate 50–80%) using a simulator or a task-generation LLM.
3. The system attempts tasks, logs all attempts.
4. At the end of a batch, the `Trainer Service` runs offline training.
5. New skills and consolidated memory facts are installed into the active system.
6. Evaluation re-runs on a calibration suite to detect regression.

### 3.4 Meta-Learning: Learning to Learn
- The system stores metadata about retrieval strategies, prompt templates, planning budgets, and exploration parameters.
- A `Meta-Policy` (a small LLM or bandit model) learns which strategies work best given the task distribution.
- This is not weight-level self-modification; it is strategy-level adaptation.

```
}
```
