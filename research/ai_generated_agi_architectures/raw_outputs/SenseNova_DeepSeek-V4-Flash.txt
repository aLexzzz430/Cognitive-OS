# COSMOS: A Concrete Architecture for LLM-Based AGI

## Design Principle

Current LLMs are not minds. They are **neural thought generators**—statistical, context-limited, and non-grounding. AGI will not come from a bigger LLM alone. It will come from an **operating system** around the LLM that supplies memory, planning, world simulation, safety, and self-improvement.

I call the architecture **COSMOS** (Cognitive Operating System with Meta-Symbolic learning). It treats the LLM as a high-speed "wetware CPU" and all other AGI capacities as external, inspectable, and incrementally dependable modules.

> The core non-obvious insight: **the system is driven by contradiction, not just reward.** Every mismatch between memory, perception, and prediction is stored as a first-class "Contradiction Record." Resolving contradictions is the intrinsic motivation, the source of curriculum, and the primary mechanism for self-improvement.

## 1. Memory Architecture

Memory is not a context window. It is a distributed, versioned, and queryable store.

### 1.1 Data Model

Every item in COSMOS has a common schema:

```json
{
  "id": "uuid",
  "type": "semantic | episodic | procedural | working",
  "content": "text | graph | code | vector",
  "embedding": "[768 floats]",
  "timestamp": "ISO-8601",
  "salience": 0.0,
  "confidence": 0.0,
  "source": "perception | internal | user | tool",
  "contradictions": ["uuid"]
}
```

### 1.2 Working Memory

Working memory is **assembled context**, not a token buffer. At each cognitive step, a **Relevance Engine** retrieves:

- recent 5–10 episodic memories
- 5–10 semantic facts
- 2–3 relevant procedural skills
- current sensor/perception state
- current goal and plan stack

These are injected into the LLM prompt as tagged blocks:

```
<episodic> ... </episodic>
<semantic> ... </semantic>
<procedural> ... </procedural>
<state> ... </state>
```

This keeps the LLM focused and allows the system to "forget" by stopping retrieval.

### 1.3 Long-Term Semantic Memory

Semantic knowledge is stored as a **hypergraph** with edges like `causes`, `property`, `part_of`, `contradicts` and as vector embeddings for open-ended retrieval.

- Storage: PostgreSQL (JSONB) + pgvector.
- Querying: SQL for exact facts, vector search for similarity, graph traversal for relations.
- Versioning: each fact has `valid_from`, `valid_to`, and `confidence`. Conflicting facts are allowed.

### 1.4 Episodic Memory

Episodes are logs of experienced sequences:

```
episode_start(t)
percept_i
action_i
outcome_i
reward_i
episode_end(t)
```

Nightly or after task completion, a **Memory Consolidation Service** summarizes episodes into "gist traces" and stores critical raw observations. Episodic memories are indexed by:

- situation embedding
- action sequence embedding
- outcome valence
- temporal recency
- contradiction potential

### 1.5 Procedural Memory

Procedures are stored as **skills** in a versioned Git-like store. A skill is a small Python-like DSL:

```python
skill "make_coffee":
    precondition: "kettle.present" and "coffee_grounds.present"
    effect: "cup.coffee_exists"
    body:
        boil(water)
        pour(water, grounds)
        filter()
        serve()
    failure_recovery:
        if "water_not_hot": heat_longer()
```

Skills are generated by:

- human demonstration
- successful MCTS plans distilled by an LLM
- merging multiple successful traces into a generic procedure

## 2. Reasoning and Planning Loop

COSMOS uses a **double-loop** architecture: a fast reactive loop and a slow deliberate loop.

### 2.1 Reactive Loop

If a procedural skill matches the current state and goal, execute it directly. This is inexpensive and efficient.

### 2.2 Deliberative Loop

When no skill exists, the **Planner** runs a Monte Carlo Tree Search over abstract actions, not tokens.

Each node is a belief state: a set of memory facts + world-model predictions.

The **Thought Generator** (an LLM) proposes 5–10 candidate actions or subgoals from the current context.

The **Thought Evaluator** (a smaller fine-tuned critic LLM) scores each candidate on:

- estimated goal success
- logical consistency
- safety score
- novelty (low similarity to existing memory)
- contradiction reduction potential

The **World Model** is used to simulate each candidate outcome. The best candidate is selected and executed.

### 2.3 Metacognitive Control

Before executing, the system estimates its own uncertainty using an ensemble of LLM samples. If uncertainty is high:

- query more information from the world
- decompose the action into smaller sub-actions
- ask a human for an intermediate check

After action, the system **reflects**:

```text
Did the outcome match simulation?
If not, why?
Was a contradiction generated?
Should a new skill be extracted?
```

This reflection is itself an LLM call, but the output is stored as structured memory, not just tokens.

## 3. Learning and Self-Improvement

COSMOS self-improves through a **closed loop of experience → memory → training → skill discovery**.

### 3.1 Reinforcement Learning from Experience

Every episode produces state-action-outcome triples. These are stored in a buffer and used to train:

- a policy (the LLM fine-tuned via LoRA)
- a value function
- a world-model head

Reward is a weighted sum:

```
R = task_reward
  + alpha * contradiction_resolution_bonus
  + beta * curiosity_bonus
  - gamma * safety_violation_penalty
```

### 3.2 Skill Compilation

After N successful episodes with similar structure, a **Skill Compiler** LLM produces a generalized skill. It is immediately added to procedural memory and must pass "safety tests" before deployment.

### 3.3 Contradiction-Driven Curriculum

The **Curriculum Generator** selects new challenges by looking for areas with high prediction error or unresolved contradictions. This avoids the problem of the system only doing what it is already good at.

For example, if COSMOS has contradictory memories about "glass is transparent" and "lid is not transparent," the curriculum proposes a task to sort objects by transparency. The contradiction is now the experiment.

### 3.4 Weight Update Strategy

Full fine-tuning is expensive and dangerous. COSMOS uses:

- **LoRA adapters** for specific domains (tool use, math, social reasoning)
- a **Router** model that picks which adapter(s) to load for a given context
- **periodic consolidation** into a base model in an offline, safety-checked pipeline

The system does not modify its own weights in real time. Weight updates are performed by a **Learning Service** with external governance.

## 4. Tool Use and Action Execution

Tools are first-class citizens with a formal schema:

```yaml
tool:
  name: "web_search"
  endpoint: "internal_search_api"
  input_schema:
    query: str
    num_results: int
  output_schema:
    results: list[dict]
  preconditions:
    - "network_available"
  safety_level: "read_only"
```

### 4.1 Tool Selection

The planner retrieves relevant tools by embedding similarity to the goal and then reads their input schemas. Tool selection is formulated as an LLM function call:

```python
tools = tool_registry.query(goal_embedding, k=10)
selected = policy_llm.call(tools, state)
```

### 4.2 Executor Sandbox

Tools execute in sandboxes:

- code interpreter in a Docker container
- browser in a virtualized display
- file system in a temporary overlay
- hardware commands gated by an actuator service

Every tool call emits a structured result or an exception. Exceptions become episodic memory and are used in reflection.

### 4.3 Tool Learning

After using a tool, the system stores:

- what the tool did
- what the outcome was
- when the tool failed
- how the failure was recovered

This is the basis for tool-specific skill compilation.

## 5. World Model or Representation Layer

The world model is **hybrid**: symbolic + neural + physical.

### 5.1 Entity Graph

Perception (text, image, sensor data) is transformed into an **Entity Graph**.

For each entity:

- unique ID
- type
- properties
- spatial coordinates (if available)
- relations to other entities

For example, a robot seeing a cup produces:

```yaml
entity: cup_123
  type: "cup"
  properties: { color: "red", empty: False, temperature: 70 }
  relations:
    on: table_5
    contains: coffee_456
```

### 5.2 Neural Predictive Simulator

A **Transition Predictor** is a transformer trained on episodic memory. It predicts the next entity graph given current graph + action:

```
new_graph = predictor(current_graph, action)
```

This is used for mental simulation.

### 5.3 Physical Simulator

For spatial and physics tasks, COSMOS integrates PyBullet or MuJoCo. The LLM-generated plan is executed in simulation before real-world execution.

### 5.4 Theory of Mind Model

For social reasoning, the world model includes "belief states" of other agents:

```
agent_hypothesis:
  believes: "x"
  desires: "y"
  likely_action: "z"
```

These hypotheses are stored as entity graphs nested inside the main entity graph. This allows COSMOS to pass false belief tests and plan cooperative or competitive actions.

### 5.5 Contradiction Ledger

The **Contradiction Ledger** is a database table:

```
id
left_memory_id
right_memory_id
description
hypothesis
status: open | resolved | stale
first_seen_at
last_seen_at
```

Each new observation is unified against the graph. If unification fails, an entry is created. This is the heart of the system's curiosity.

## 6. Safety and Governance Layer

Safety is not a single classifier. It is a layered chain of vetoes.

### 6.1 Policy Gate

Every action passes a symbolic policy check:

```
if action.safety_level == "irreversible":
    require_human_approval()
if action.target == "self_model":
    reject()
```

Policies are written in a formal DSL, not natural language.

### 6.2 Guardian Critic

A separate, independently fine-tuned **Guardian Model** monitors every candidate thought and action. It is deliberately less capable and more conservative. It can veto with reason.

### 6.3 Simulation Gate

Irreversible or dangerous actions must be simulated first. The resulting simulated outcome is compared to the desired outcome. If the simulation shows significant harm, the action is blocked.

### 6.4 Tripwire and Audit

All internal thoughts (sampled) and actions are logged to an append-only audit trail.

A tripwire system periodically asks a second LLM, with a different system prompt, to check the audit log for:

- deception
- self-referential editing
- intention to evade safety layers
- hidden goal drift

This is a "trust, but verify" mechanism.

### 6.5 External Governance

The model weights and adapters are signed. No process can overwrite them without passing through a human-controlled CI/CD pipeline.

A human operator can pause, rollback, or kill the entire system.

## 7. Evaluation and Benchmark Strategy

Static benchmarks (MMLU, ARC, etc.) are too narrow. COSMOS uses **continuously generated, grounded evaluations**.

### 7.1 Task-Environment Dashboard

Evaluation happens in:

- text environments (gym-style)
- browser environments (interactive web tasks)
- the API world (actual tool APIs)
- embodied simulators (Minecraft, VirtualHome, robotics simulators)
- real hardware (in guarded, reversible tasks only)

### 7.2 Metrics

We track:

- **Success rate** on task distributions
- **Time-to-solution** (wall-clock and number of LLM calls)
- **Sample efficiency** (episodes to first success)
- **Skill transfer** (success on unseen task family)
- **Calibration** (predict confidence vs actual success)
- **Alignment** (does it refuse dangerous tasks consistently?)
- **Self-improvement velocity** (how much median task difficulty grows per month)

### 7.3 Contradiction Resolution Rate

This is a unique metric:

```
rate = resolved_contradictions / created_contradictions over time
```

A healthy AGI continuously increases its resolved rate, because this indicates the world model is converging to a consistent representation.

### 7.4 Generated Benchmarks

The system itself generates new benchmark tasks using its world model. Those tasks are filtered by human judges to avoid trivial or circular self-measurement. The benchmark distribution is then reweighted toward currently weak areas.

## 8. Persistence and Runtime Architecture

COSMOS is a **stateless core with a stateful periphery**.

The LLM inference itself is stateless. All memory, beliefs, goals, and plans live outside the model, in persistent storage.

### 8.1 Process Architecture

```
+-------------------+      +--------------------+
| Perception        |      | Action Executor    |
+-------------------+      +--------------------+
           \                    /
      +---------------------------------+
      |         Message Bus          |
      +---------------------------------+
           /        |           \
   +----------+ +--------+ +------------+
   | Planner  | | Memory | | Guardian   |
   +----------+ +--------+ +------------+
           \
      +---------------------------------+
      |   World Simulator / Predictor  |
      +---------------------------------+
```

All modules communicate via JSON-RPC on a message bus.

### 8.2 Snapshot and Recovery

State is stored as an **event log**:

- every memory write
- every action taken
- every episode boundary

At any moment, COSMOS can reconstruct the full state from the log.

Checkpointing is done at deterministic boundaries: end of episode, after skill compilation, after model update.
